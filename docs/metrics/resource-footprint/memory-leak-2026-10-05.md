# 内存泄漏

## 结果

装出来的 Lens 起一次，每 30 s 采一次，采 10 分钟，两轮：改前是基线包，改后是减过四项的包（见同目录
`package-size`）。数字是私有字节与句柄数，两头各取首末两点：

| | 私有字节 起 → 末 | 差 | 句柄 起 → 末 | 差 |
| --- | ---: | ---: | ---: | ---: |
| 改前 | 155.85 → 155.69 MB | −0.16 | 2782 → 2779 | −3 |
| 改后 | 156.52 → 156.50 MB | −0.02 | 2782 → 2778 | −4 |

两轮都没有单调上涨：曲线是平的，末点比首点略低。W1 改的是路径（数据目录、设置目录）与打包，不碰任何东西
的生命周期，所以这里的两列是**回归核对**（改前改后一致），不是优化前后的对比。

## 一次性的台阶（真实使用那一段）

改前那一轮采到第 11 个点时（t≈300 s）数字跳了一档：私有字节 155.69 → 216.42 MB，句柄 2779 → 4413，
线程 72 → 154。原因是读者本人正在 Chrome 里选词，装出来的这个实例的鼠标钩子接到了那 9 次选区，第一次
把选区动作条真正画了出来。跳完之后 90 s 内不再涨（216.42 → 219.34 → 219.09 → 219.03），这 90 s 里也
又画了几次：

| 时刻 | 私有字节 | 句柄 | 线程 |
| --- | ---: | ---: | ---: |
| t=270 s，还没画过任何表面 | 155.69 MB | 2779 | 72 |
| t=300 s，第一次画出动作条 | 216.42 MB | 4413 | 154 |
| t=330 s | 219.34 MB | 4446 | 154 |
| t=360 s | 219.09 MB | 4454 | 156 |
| t=390 s | 219.03 MB | 4450 | 154 |

读法：**首帧代价，不是每次使用的增长**。第一次渲染要建 D3D 设备、编译着色器、让驱动起它自己的线程池，
于是句柄与线程一次性抬上去；此后同样的动作不再有台阶。空闲态（`idle-memory` 报告里那 156 MB）是 “什么都
没画过” 的水位，用过之后停在 219 MB 左右。

那 9 次选区没有发出任何请求（日志里 `LlmClient::explainWords` 的 `explaining … item(s)` 出现 0 次）：动作条
要读者按一下才会发请求，而没有人按。

## 没覆盖到的

- **表面的反复开关没有脚本驱动**。九个窗口是启动时建好、靠 `visible` 开关的，开一百次会不会涨，这一份
  答不上来：`TEST.md` §5 已经写明托盘菜单那几张只能请人看，W1 没有为它新建驱动手段（在 `src/` 里加计时器
  或探针是明令禁止的）。
- **长时间运行**只测了 10 分钟一轮。托盘常驻应用的 “长” 是数天，这一轮不足以说数天的事。
- 上面那张表里的 219 MB 是**读者自己操作**撞出来的样本，不是设计好的负载；它证明的是 “画第一次有台阶、
  之后不涨”，不是 “画一次只涨一点点”。

## 数字来源

`test/records/w1-idle-memory-before.txt`、`w1-idle-memory-after.txt`（gitignored，本机运行记录）；采样脚本
`test/records/w1-soak.ps1`（同样 gitignored）。读的是 `Get-Process` 的 `PrivateMemorySize64` /
`HandleCount` / `Threads.Count`。改后那一轮全程 `selectionCapture=false`，所以曲线是干净的。
