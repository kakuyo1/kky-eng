# 覆盖率报告

这一份盖两条线：`src/` 下的 C++ 行，与 QML 模块里被求值的表达式位置。两条线的工具、口径、分母构造方式都不同，**读数不可比，也不许平均**。想补哪一块看 [`docs/coverage-plan-2026-10-03.md`](../coverage-plan-2026-10-03.md)。

## 1、报告信息

| 项目 | C++ 一条线 | QML 一条线 |
| --- | --- | --- |
| 分析范围 | `src/` 下被测试目标链进去的源文件与头文件 | `src/app/qml/` 下的模块文件 |
| 工具 | `OpenCppCoverage 0.9.9.0`（winget 安装） | `qmlprofiler`（随 Qt 6.9.0）+ `tree-sitter-qmljs 0.3.1` |
| 采集方式 | 对 `build-ninja` 已有的 Debug 二进制逐个插桩，五份结果合并成一份 Cobertura XML | 两个 QTest 目标各跑一遍 QML profiler，取 trace 里出现过的 `{文件, 行}`，除以解析树里的可求值位置数 |
| 单位 | 机器码行 | 绑定 / signal handler / 函数的位置 |
| 原始数据 | `test/records/coverage/coverage.xml` | `test/records/qmlcov/qml-coverage.json` |
| 构建树 | 两者都是 `build-ninja`（Debug），都不新建树、不改构建标志 | 同左 |

本报告只回答 “哪些东西被测试跑过”，不回答 “跑过的结果对不对”。一行被执行过，不等于它产生的结果被断言过——断言的覆盖情况要另看用例本身。

## 2、执行摘要

C++ 行覆盖 66.0%（998/1511）；QML 执行覆盖 80.4%（589/733）。

`src/` 下 21 个文件报出了可执行行，共 1511 行，其中 998 行被执行。

被测试得最厚的是持久化与纯函数层，最薄的是网络链路与启动编排：

| 模块 | 文件数 | 覆盖行 | 可执行行 | 行覆盖率 |
| --- | ---: | ---: | ---: | ---: |
| `src/core` | 7 | 421 | 516 | 81.6% |
| `src/llm` | 6 | 227 | 306 | 74.2% |
| `src/app` | 8 | 350 | 689 | 50.8% |
| 合计 | 21 | 998 | 1511 | 66.0% |

四个读数最低的文件，各自的成因不同：

- [`llm_client.cpp`](../../src/llm/llm_client.cpp) 12.7%（8/63）：真模型往返要走网络，`lens_gtest_smoke` 需要 key 且花钱，本轮没跑。
- [`profile.cpp`](../../src/core/profile.cpp) 19.0%（11/58）：这棵树的 `LENS_ENABLE_PROFILE` 是关的，测量点编译成了空，读的低是构建配置的结果，不是测试缺口。
- [`selection_text_grabber.cpp`](../../src/app/selection_text_grabber.cpp) 36.7%（72/196）：抓取路径要真的有别的窗口当前台，那条用例默认 skip。
- [`app_controller.cpp`](../../src/app/app_controller.cpp) 43.6%（136/312）：`main()` 的编排（日志、配置、翻译、托盘、钩子的接线）只在 `lens.exe` 里跑，没有任何测试目标覆盖它。

另有 8 个 `src/` 文件一行都没报出来，原因见 3.3——那是口径，不是 0% 覆盖率。

**CI 上报的两个数与上面这两个都不相等，而且原因不一样，两边都要看。**第一次 CI 运行报出来的是 C++ 55.2%（815/1476，20 个文件）与 QML 83.9%（606/722）：

- C++ 那条线，CI 只跑四个目标，本机默认跑五个。少的那个是 `lens_gtest_integration`，而它恰好覆盖 `selection_text_grabber.cpp` 与 `mouse_selection_hook.cpp` 的大半，所以 `src/app` 从 50.8% 掉到 28.1%，总量跟着掉十一个点。这不是 CI 量得差，是两份口径本来就是两个分母。
- QML 那条线，两份数不同不是因为目标不同，是因为**树不同**：CI 检出的是提交后的版本，本机量的是当时的工作区，而另一条线上的人正在改 `TrayMenu.qml`。同一个文件在 CI 上读 84%，在本机读 52%。下面 §5 的表是本机那一次。

一个数的完整说法要带上它在哪棵树上、跑了哪几个目标，否则对不上就只会以为是错的。

## 3、C++ 一条线的范围与口径

### 3.1 工具与为什么是它

这台机器上原本没有任何覆盖率工具：`gcov`、`llvm-cov`、`clang-cl`、`OpenCppCoverage` 都不在 PATH 上，`D:\VS 2022\VC\Tools\Llvm\x64\bin\` 里只有 `clang-format.exe` 和 `clang-tidy.exe`，VS 是 Community 版，没有随附 `Microsoft.CodeCoverage.Console.exe` 或 `CodeCoverage.exe`（`VSInstr.exe` 在，但少了产出 `.coverage` 的那一半）。

选 `OpenCppCoverage` 的理由是它唯一不需要动构建：它读二进制的 PDB 在运行时插桩，所以既不新建覆盖率树，也不加编译标志，被测量的对象就是 `build-ninja` 里那批 Debug 产物。clang-cl 那条路要先把 LLVM 装上（本机只有 `clang-format.exe` 和 `clang-tidy.exe`，没有 `clang-cl`），是三条里代价最大的一条，所以排最后。

### 3.2 哪五个目标在跑

`scripts/coverage.sh` 依次覆盖能无人值守跑完的五个目标：

| 目标 | 用例数 | 本轮结果 |
| --- | ---: | --- |
| `lens_gtest_unit` | 29 | 29 绿 |
| `lens_gtest_perf` | 1 | 绿 |
| `lens_gtest_integration` | 15 | 13 绿、1 skip、1 红 |
| `lens_qtest_components` | 38 | 38 绿 |
| `lens_qtest_surfaces` | 23 | 23 绿 |

`lens_gtest_smoke` 不在内：它要 `settings.local.json` 里的 key，且会花钱。

一个目标退出非零不影响它已经跑过的部分进入统计——`lens_gtest_integration` 是红的，它的覆盖照样算进来了。

### 3.3 没有行数据的 8 个文件

`src/` 下这 8 个文件在 Cobertura 里没有出现，不等于它们 0% 覆盖，而是没有可归因的可执行行：

- `app/main.cpp`、`llm/qt_log.cpp`：只被 `lens.exe` 引用。测试目标是静态链接的，链接器不会把没人引用的目标文件拉进来——`qt_log.cpp` 只导出 `installQtMessageHandler()`，而它只在 `main.cpp` 里被调用。可以验证：`lens.exe` 里有 `qt: {}` 这个字面量，五个测试二进制里都没有。
- `core/filter_core.h`、`core/log.h`、`core/profile.h`、`llm/llm_pure.h`、`llm/llm_protocol.h`、`llm/qt_log.h`：声明、宏和注释，编译器没有从中生成可执行行。`log.h` 的日志宏在调用点展开，行算在调用者身上。

QML 不在这条线里：`OpenCppCoverage` 只插桩机器码，QML 走的是完全不同的另一条路，在 §5。

### 4.2 一个已知的红例

`lens_gtest_integration` 的 `SelectionHook.ReportsASynthesisedDragAtItsReleasePoint` 本轮失败，报的是 `the hook reported nothing, so the gesture rule rejected a drag of 40 px`，并且稳定复现（连跑三次都一样）。它在 `ccdaefc` 这个干净检出上同样失败，所以不是本轮工作树里的改动引起的。

失败的过程是：钩子装在它自己的线程上，`install()` 在 `SetWindowsHookExW` 返回后放行；测试紧接着 `SendInput` 送出按下、移动、抬起三个事件。怀疑是那三个事件送在钩子线程进入消息循环之前，被系统按超时丢掉——测试等满 2000 ms 的那次超时，所以六次运行的耗时都落在 2019–2056 ms 之间。这是推测，没有验证；验证要改测试本身，不在本次范围内。

`mouse_selection_hook.cpp` 的 80.0% 是在这条用例失败的前提下拿到的，而且它不稳：同一棵树上的三次运行里，两次读 88 行、一次读 97 行——测试等满超时之前，钩子有时收得到那几个事件，有时收不到。修好这条用例之后，这个数才会钉住。

## 5、QML 执行覆盖率

Qt 没有 QML 的行覆盖率工具，这条路的取舍见 `TEST.md` §4 与 `scripts/qml-coverage.js` 的文件头，`src/app/qml/` 的规模与结构见 [`src-quality-2026-10-03.md`](src-quality-2026-10-03.md)。简单说：QML 里真正 “执行” 的是 JavaScript——属性绑定、signal handler、函数——而 profiler 恰好对每一次求值都记一条带文件与行号的事件，所以执行集有据可查。分母来自 `tree-sitter-qmljs` 的解析树：模块里每个非字面量的 `ui_property` 与 `ui_binding`，加上每个 `function_declaration`。

- **未执行的 144 个位置里有 37 个是 `qsTr()` 标签。**无头跑不渲染，标签绑定永不求值。这不是缺口。真正没被点到的手（托盘菜单的语言下拉、设置面板的 Save / Defaults、气泡上的 “已知 / 新词”）在 [`docs/coverage-plan-2026-10-03.md`](../coverage-plan-2026-10-03.md) §4.1 里列着。

## 6、接下来做什么

补测的清单、顺序与判据写在 [`docs/coverage-plan-2026-10-03.md`](../coverage-plan-2026-10-03.md)，本报告不重复。一句话：先修 §4.2 那条红例，再按 “离线纯函数 → 网络接缝 → 真机失败分支 → QML 的手” 的次序推。

两个数都**不设阈值**。同一棵不改的树，C++ 那条线会在 66.0%–66.6% 之间自己摆（§4.2），QML 那条线的分母又混着口径造成的空位，拿它们卡构建会卡在天气上。要做趋势就按日期存报告比。CI 现在每次跑完会把两份原始数据传成 artifact，不卡构建。

## 7、复现命令

先按 `AGENTS.md` 的 Build 一节构建，再：

```bash
sh scripts/coverage.sh            # C++，写 test/records/coverage/
sh scripts/qml-coverage.sh        # QML，写 test/records/qmlcov/
```

`coverage.sh` 默认跑五个能无人值守跑完的目标，也可以只点名几个：`sh scripts/coverage.sh test/records/coverage lens_gtest_unit`。CI 就是这么调的（`lens_gtest_integration` 要真鼠标和真剪贴板，runner 上没有）。最后那行汇总由 `scripts/coverage-summary.py` 算出——Cobertura 文件里，一个被多个测试二进制链进去的源文件会出现多份，根节点把这几份加在一起，直接读会偏低，这个脚本按文件对行号取并集。

`qml-coverage.sh` 需要 `node_modules`（`npm ci`）与 Qt 的 `qmlprofiler`，两者都在 PATH 上时它会自己找到。两份原始数据就是上面所有数字的出处，报告是按它们转写的。

C++ 那条线的工具要求 `OpenCppCoverage.exe` 在 `C:\Program Files\OpenCppCoverage\`，找不到时脚本会先查 PATH、再报错退出。安装：

```powershell
winget install --id OpenCppCoverage.OpenCppCoverage -e
```

读数取自 `build-ninja`，那棵树的内容是 `ccdaefc` 加当时未提交的改动。

同一棵树上连跑三次，只有 `mouse_selection_hook.cpp` 动了：两次是 88/110，一次是 97/110，其余 20 个文件逐位相同。总量因此在 998–1007 行之间摆，也就是 66.0%–66.6%。摆动全部来自 §4.2 那条红例的等待窗口。

QML 那条线也摆，原因有两个而不是一个：重建前后的 `TrayMenu.qml` 差 19% 与 52%（上一节），而同一次构建的两轮 trace 之间事件数也会小幅浮动（`Binding` 935–1006，`HandlingSignal` 40–44）。上表报的是落在 `test/records/qmlcov/qml-coverage.json` 里的那一次。
